# 1. Подсчёт суммы 10 млн чисел

Для эксперимента был создан файл `numbers.txt`, содержащий 10 000 000 целых чисел от 1 до 10 000 000.

Ожидаемая сумма:

```text
50000005000000
```

Сумма была вычислена тремя способами:

1. Последовательно.
2. С использованием 4 потоков `threading`.
3. С использованием 4 процессов `multiprocessing`.

Каждый вариант запускался 3 раза. Для сравнения использовалась медиана времени.

## Результаты

| Метод | Запуск 1 | Запуск 2 | Запуск 3 | Медиана |
|---|---:|---:|---:|---:|
| Последовательно | 0.1988 с | 0.2014 с | 0.1894 с | **0.1988 с** |
| 4 потока | 0.2524 с | 0.2459 с | 0.2488 с | **0.2488 с** |
| 4 процесса | 0.4046 с | 0.3912 с | 0.4065 с | **0.4046 с** |

Во всех трёх вариантах получена одинаковая сумма:

```text
50000005000000
```

## Анализ

В данном эксперименте последовательный вариант оказался самым быстрым:

```text
Последовательно: 0.1988 с
4 потока:        0.2488 с
4 процесса:      0.4046 с
```

Подсчёт суммы является CPU-bound задачей, то есть основная работа выполняется процессором.

В CPython существует GIL (Global Interpreter Lock), который ограничивает одновременное выполнение Python bytecode несколькими потоками внутри одного процесса. Поэтому использование 4 потоков не дало ускорения.

Более того, при использовании потоков появляются дополнительные расходы на создание потоков и переключение между ними.

Процессы позволяют обходить ограничение GIL, поскольку каждый процесс имеет собственный интерпретатор Python. Однако процессы требуют больше ресурсов, а передача больших частей списка между процессами создаёт дополнительные накладные расходы.

Поэтому в данном эксперименте процессы также оказались медленнее последовательного варианта.

# 2. Сетевая задача

Для проверки многопоточности с вводом-выводом были выполнены 20 HTTP-запросов к локальному HTTP-серверу.

Были протестированы:

1. Последовательная загрузка.
2. `ThreadPoolExecutor` с 4 потоками.
3. `ProcessPoolExecutor` с 4 процессами.

## Результаты

| Метод | Время |
|---|---:|
| Последовательно | **0.1699 с** |
| ThreadPoolExecutor — 4 потока | **0.0281 с** |
| ProcessPoolExecutor — 4 процесса | **0.2307 с** |

Все 20 запросов были успешно выполнены.

## Анализ

Сетевая задача является I/O-bound задачей.

При выполнении HTTP-запроса программа значительную часть времени ожидает ответ. В это время другой поток может выполнять другой запрос.

Поэтому `ThreadPoolExecutor` показал значительно лучший результат:

```text
Последовательно: 0.1699 с
4 потока:        0.0281 с
4 процесса:      0.2307 с
```

Использование 4 потоков позволило значительно уменьшить время выполнения.

Процессы в данном случае оказались неэффективными из-за дополнительных расходов на создание процессов и взаимодействие между ними.

# 3. GIL

GIL (Global Interpreter Lock) — механизм CPython, который не позволяет нескольким потокам одновременно выполнять Python bytecode внутри одного процесса.

Для CPU-bound задач это ограничивает возможность получить ускорение от нескольких потоков.

Поэтому для вычислительных задач:

```text
CPU-bound:
потоки → обычно не дают ускорения
процессы → позволяют использовать несколько ядер
```

Для I/O-bound задач ситуация отличается:

```text
I/O-bound:
потоки → хорошо подходят
процессы → часто имеют лишние накладные расходы
```

Полученные результаты подтверждают это различие.

Для подсчёта суммы последовательный вариант оказался быстрее потоков.

Для сетевой задачи 4 потока оказались значительно быстрее последовательного выполнения.

# 4. Разделение памяти

Для проверки разделения памяти был создан список:

```python
[1, 2, 3]
```

## Поток

Поток добавил в список число `4`.

Результат внутри потока:

```text
[1, 2, 3, 4]
```

После завершения потока родительский код также получил:

```text
[1, 2, 3, 4]
```

Это показывает, что потоки одного процесса используют общее адресное пространство.

## Процесс

Отдельный процесс добавил в свой список число `5`.

В процессе результат был:

```text
[1, 2, 3, 5]
```

Однако после завершения процесса родительский процесс получил:

```text
[1, 2, 3]
```

Изменение не сохранилось в родительском процессе.

Это показывает, что обычные процессы имеют отдельные адресные пространства.

# 6. Общий вывод

В ходе практической работы были изучены потоки и процессы в Python.

Для CPU-bound задачи подсчёта суммы 10 млн чисел многопоточность не дала ускорения. Последовательный вариант оказался самым быстрым.

4 потока выполняли задачу немного медленнее из-за ограничения GIL и дополнительных расходов на работу с потоками.

4 процесса также оказались медленнее в данном эксперименте из-за накладных расходов на создание процессов и передачу больших объёмов данных между ними.

Для I/O-bound сетевой задачи 4 потока показали значительное ускорение. Это связано с тем, что во время ожидания сетевого ответа другие потоки могут продолжать работу.

Также экспериментально было показано различие в памяти:

- потоки используют общее адресное пространство;
- процессы имеют отдельные адресные пространства.

Таким образом, выбор между потоками и процессами зависит от характера задачи:

- **CPU-bound → процессы**
- **I/O-bound → потоки**

В данной практической работе были реализованы и исследованы оба варианта.
